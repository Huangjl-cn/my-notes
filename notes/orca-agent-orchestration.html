一句话定位：多 Agent 协作的协调层

单个 Agent 能干活，但「多个 Agent 如何并行干活、如何互通消息、如何追踪进度、如何收尾」是另一层问题。Orca 编排就是这层协调层：它不替 Agent 干活，只负责把任务派出去、把消息传到位、把结果收回来。能力总览如下：

能力具体是什么
并行派活把若干任务同时分给不同 Agent（每个在自己独立的工作区里），互不干扰
任务工单（DAG）任务可声明依赖，Orca 判定谁 ready、谁等谁
Agent 间消息互相发消息：支持类型/优先级/线程，可追问可回复
生命周期上报被派发的 Agent 干完主动报告，系统自动结算任务；卡住可求助
决策门协调者可在关键节点挂起任务，等人拍板再放行
失败重试与熔断同一任务可重派，连续失败自动标记 failed
资源收尾worker 完成后释放/保留其终端，输出留档可再审
跨服务器通过稳定逻辑地址把 worker 派到远程 Orca 服务器
三个核心概念：Run / Task / Dispatch

所有编排状态都挂在三个概念上，它们是后面所有 CLI 命令和 SQL 表的主线。从存储视角看，run_id 是几乎所有表的关联键：

存储结构 · 三个概念的挂载关系
runs 表（run_xxx）── run_id 是所有表的 FK ├── tasks（task_1）：spec / status / deps └── dispatch_contexts + worker_dispatches： task_id + terminal handle + 状态 → 派发时把 preamble（任务书）注入 Agent 会话 → Agent 做完发 worker_done（task_id + dispatch_id） → 自动：task completed / dispatch settled

三个概念的生命周期差异是理解它们的关键——Run 是会话级容器，Task 是一份声明，Dispatch 是一次具体执行：

RunTaskDispatch
生命周期长（一个会话一个）中（可能重派）短（一次执行）
作用命名空间 + 协调者收件箱描述「做什么」这次派谁干、干得怎样
不做什么不调度任何东西无执行者——
单协调者模型：Run 与终端的绑定

后面会反复看到 check 命令不带 --run 也能工作——默认查的是「哪个信箱」？答案藏在 runs.coordinator_handle 字段里。run-create 时，创建者终端（或 --from 指定终端）自动成为该 Run 的唯一协调者，写进绑定字段；此后 check 的默认目标就是当前终端绑定的 Run。

绑定关系有三条建立途径：

1
run-create — 创建即绑定，创建者终端成为协调者
2
run-use --id <run_id> — 显式绑定/切换
3
worker 被 dispatch 时自动绑定 — 所属 Run 由注入的 preamble 指定
多编排者互不干扰：A 终端的 Run 和 B 终端的 Run 是两个独立信箱——即使都不传 --run，各自 check 各自绑定的 Run。这是「单协调者模型」的直接结果：一个 Run 只有一个消费入口。
例外与显式 --run：未绑定的 Run、共享与 takeover

未绑定例外：恢复/兼容路径产生的 Run（如 legacy_adoptions）可能 coordinator_handle=NULL。此时 check 没有默认目标，必须显式 --run。

什么时候要显式 --run：从非绑定终端调用、脚本化/幂等调用、run-use 之后想确认、上下文不明时——显式声明，避免依赖隐式绑定。

share 一个 Run 不是并行：旧协调者会被 fence（只读），新协调者通过 run-use --takeover-legacy 接管后才拥有消费权——设计上依然是「单协调者模型」，不是多消费者广播。

一条任务的完整生命周期

从立项到 git 合并，一条任务走七步。前三步是「立项—建工单—派活」：Run 是协作会话的容器，Task 是纯声明（还没人做），worker-start 一步完成开 worktree 终端、注入任务书、派发三件事。

BASH · 步骤 1–3 · 立项与派活
# ── 1. 立项：一个 Run = 一次协作会话 ── orca orchestration run-create --objective "登录功能前后端开发" # → run_abc123（之后所有东西都挂在这个 run_id 下） # ── 2. 建工单：Task 描述「要做什么」（纯声明，还没人做）── orca orchestration task-create --spec "后端实现 /api/login" orca orchestration task-create --spec "前端实现登录页" --deps '["<task1>"]' # → task_100 / task_200 # ── 3. 派活：worker-start = 开 worktree 终端 + 注入任务书 + 派发 ── orca orchestration worker-start --task task_100 --worktree tmp-backend --agent pi orca orchestration worker-start --task task_200 --worktree tmp-frontend --agent pi # → 每个 worker 拿到一个 dispatch 身份（taskId + dispatchId）

后四步是「等待—上报—收尾—合并」：协调者阻塞等待特定类型的消息，worker 干完主动上报，协调者结算后释放 worker，最后在 git 层合并各分支。

BASH · 步骤 4–7 · 等待、上报与收尾
# ── 4. 协调者等结果（阻塞，等特定类型消息）── orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 900000 # ── 5. worker 端：被派发的 Agent 做完后上报 ── orca orchestration send --type worker_done --task-id task_100 --dispatch-id <d1> \ --outcome succeeded --files-modified "src/a.java" --body "完成摘要" # ── 6. 协调者收到后收尾：复用或释放该 worker ── orca orchestration worker-release --dispatch <d1> # ── 7. 最后在 git 层合并各分支（push + PR 或本地 merge）──
run-create 的绑定语义：为什么 check 不带 --run 也能工作

步骤 1 里藏着一个关键默认行为：run-create 默认把「当前终端」（或 --from 指定终端）绑定为该 Run 的协调者，即 runs.coordinator_handle = 绑定终端 handle——单协调者模型。

因此后续 check 不带 --run 时，默认检查的就是「这个终端绑定的 Run」。多个编排者各自 run-create → 各自绑定，check 互不干扰。

例外：恢复/兼容路径产生的 Run 可能未绑定（coordinator_handle=NULL），此时 check 必须显式 --run。

协调者与 worker 的「电话本」

编排的前提是找得到人：先定位工作区，再定位工作区里的 Agent 终端（拿到 handle），然后才谈得上发消息。工作区发现命令对所有项目可见：

BASH · 发现与通信
# 找工作区（所有项目的工作树都能看到） orca worktree list --json # 找某工作区下的 Agent 终端（拿 handle） orca terminal list --worktree name:tmp-frontend --json # 读了/写了，但不用编排时（轻量提醒）： orca terminal send --terminal <handle> --text "继续" --enter --json # 需要追踪的协作消息： orca orchestration send --run run_abc123 --to <run|dispatch> --subject ... --body ... --json orca orchestration check --run run_abc123 --format --json orca orchestration reply --id <msg_id> --body "..." --json

上面出现了三个基础概念——worktree、handle、runtime。它们是理解 Orca 的前置知识，展开即可，不影响主线：

worktree 是什么：git 的「一个仓库多份工作区」

每个 worktree 有独立的工作区文件 + 私有 HEAD/index，但共享同一个对象库和全部分支。多个 Agent 各占一个 worktree，git add/commit 互不干扰，最后各自分支 merge 回主线。

worktree 的 .git 只是一个约 100 字节的指针文件（gitdir: 主仓库/.git/worktrees/<id>），不复制对象库——所以「每个 Agent 一份工作区」的磁盘开销远小于完整 clone。

handle 是什么：PTY 注册表的 key

Runtime 给每个 Agent 终端会话发的 UUID（形如 term_xxx），是 PTY 注册表的 key。

注意它的生命周期：Runtime 重启后失效，需要重新 terminal list。需要长期稳定的逻辑地址时，用 dispatch:<id> 而不是 handle。

runtime 是什么：真正干活的常驻服务

Orca 后台真正干活的常驻服务（Electron 主进程，或 orca serve 无头运行）。

所有 CLI 命令都是发到它的 JSON-RPC；它持有全部 PTY、写 SQLite、跑编排逻辑。CLI 只是薄薄一层外壳。

两种「发消息」的取舍

找到终端之后，Orca 提供两种发消息的方式。它们的底层是两条完全独立的管道（下一 Tab 展开），选择哪种，本质是选择「即时送达」还是「落库追踪」：

场景用哪个
一句话提醒、打断、给指令terminal send（即时，像人打字）
任务书、工单、需要对方确认收到orchestration send（落库，可追踪，对方 check 拉取）
worker 干完汇报 / 被卡住求助send --type worker_done / question / escalation
协调者回 worker 的问题reply --id <msg_id>
一句话判断：消息丢了无所谓、越快越好 → terminal send；需要留痕、需要 ack、需要线程化追问 → orchestration send。
Worker 的三类上行信号

除了普通的 send 状态消息，worker 还有三类上行信号。它们语义不同，且各自有独立的表/字段支持：

信号语义实现落点
ask向协调者问阻塞性问题，等回复再继续question_threads 行，pending → answered → closed
heartbeat报活：我还在干活更新 dispatch_contexts.last_heartbeat_at
escalation升级求助：自己干不动了，需要协调者介入与 question 类似但语义更强，协调者可介入或重派

ask 的用法——worker 端默认投到所属 Dispatch 的 Run，协调者端用 reply 回答：

BASH · ask / reply
# worker 端（默认投到所属 Dispatch 的 Run） orca orchestration ask --question "接口返回结构是 X 还是 Y?" --options "X,Y" --timeout-ms 600000 # 协调者端 orca orchestration reply --id <msg_id> --body "用 X"

heartbeat 携带 JSON payload 标明自己干到哪个阶段：

BASH · heartbeat
orca orchestration send --type heartbeat --subject "alive" \ --payload '{"taskId":"...","dispatchId":"...","phase":"implementing"}'
heartbeat ≠ 干完了。协调者看到 heartbeat 只说明 worker 还活着。另外 worker_done/heartbeat 是 Dispatch 级信号——省略 --to 即用所属 Run，不能发 group。

escalation 是语义最强的求助——worker 判断「自己干不动了 / 需要协调者接管」：

BASH · escalation
orca orchestration send --type escalation --subject "阻塞" --body "需要你介入..." \ --task-id X --dispatch-id Y

协调者收到后通常在 worker 继续等待时介入处理，或决定重派。

ask 的实现：question_threads 与幂等 resume

ask 创建 question 类型消息 + 一行 question_threads 记录（status=pending），然后阻塞等待回复。

超时/断连后 question 保持 pending，不会丢：协调者可随时 reply --id 补答，worker 也可用 ask --resume <msg_id> 恢复等待——resume 是幂等的，不新建问题。

reply --id X 生成的新消息带 thread_id=X，与原问题串成线程；answer_message_id 指向这条回复消息。

worker_done 的唯一性与收尾三选一

worker 只能发一次 worker_done（带 --outcome succeeded|failed），发完必须结束该轮，idle 在 agent 提示符。协调者收到后三选一：

1
复用 — 同一 worker 立即接下一个 Task：worker-start --task <next> --terminal <handle>
2
保留 — 用户要求调试：worker-retain --dispatch <id>
3
释放 — 默认动作：worker-release --dispatch <id>，关掉该 dispatch 专属的终端，输出已存档、可用 worker-read 再读

「只能发一次」不是靠自觉，而是结算前的身份校验——发送方必须就是被派发的那个终端：

JS · worker_done 校验逻辑（截取）
// 校验 dispatch.assignee == from_handle 且 taskId/dispatchId 匹配 if (dispatch.assignee === from && dispatch.taskId === taskId) { task.status = outcome === 'succeeded' ? 'completed' : 'failed' dispatch.status = 'settled' // 3 次失败 → task.status = 'failed'（熔断） }
校验把「谁有资格汇报」钉死了：dispatch.assignee 必须等于发送方 handle，且 taskId/dispatchId 匹配——防止无关终端伪造完成消息。结算 automatic：task 状态随 outcome 翻转，dispatch 记为 settled。
派活的两种方式与任务依赖

派活有高低两个入口：worker-start 是一步到位的推荐入口；dispatch --inject 是低层原语，只做「派发 + 注入」，终端要自己先建：

worker-start（推荐）dispatch --task X --to <h> --inject（低层）
组成worktree/终端 + 派发 + 注入，合一步仅派发（终端要自己先建）
返回完整 receipt（ready/effects/residualResources）仅派发状态
监控有（worker-show/read/stop/release 全套）无（operator 启动的终端视为 unsupervised）
何时用默认自定义 argv（如 codex 定制 model/effort）、特殊拓扑
注入自动注入 preamble--inject 才注入

worker-start 的调用形态是三件事的合成：worktree 复用/新建 + terminal create + dispatch --inject，返回 { worktree, terminalHandle, dispatchId, effects }。

unsupervised 陷阱：dispatch --inject 派发的 worker 没有对应的 worker_dispatches 行——worker-stop/worker-release 不会关闭它的进程，资源仍归 operator。要可管理，必须用 worker-start。
嵌套深度限制：depth 字段与 nested_worker_depth_exceeded

dispatch_contexts.depth 记录派发链的嵌套层级：root 协调者的 worker = 1，worker 的 worker = 2，以此类推。

规则
默认 depth=1 → worker 再派子 worker 会报 nested_worker_depth_exceeded 可在 Settings → Orchestration → Nested worker depth 调大 计数从「发出命令的终端」算起，新建 Run 不会重置

这是一个防失控设计：不设上限的话，worker 派 worker、子 worker 再派子 worker，进程树会指数膨胀。

任务依赖（DAG）的判定是事件驱动的——依赖任务完成的事件触发对下游任务的状态检查：

依赖满足的过程 · T3 依赖 T1、T2
task-create(T3, deps=[T1,T2]) ├─ 依赖不全 → T3.status='blocked'（不占 Agent；此时 dispatch 会报错拒绝） ├─ T1 完成（worker_done）→ 事件触发检查：依赖不全 → 仍 blocked ├─ T2 完成（worker_done）→ 事件触发检查：依赖全满足 → T3.status='ready' ← 自动！ └─ 协调者 dispatch T3 → 成功 → Agent 开跑
ready 是「自动变」但「不自动派」：依赖完成事件驱动 blocked→ready，但开跑仍需协调者 dispatch——资源与优先级由协调者决定。dispatch 前置校验要求任务必须 ready（否则报错 Task ... is not ready ... ready tasks can be dispatched）；ready 任务已有活跃 dispatch 时也会拒绝重复派发。协调者的节奏通常是：task-list --ready 拿新就绪任务 → dispatch → 等 worker_done → 再派下一波。
核心结论：两条完全独立的通信管道

两种发送方式背后，是 Runtime 里两条互不相干的通道。实时管道直接往终端写字节；持久管道把消息写进 SQLite，等对方来拉：

实时管道 · terminal send
  • PTY 直写：node-pty.write()
  • 对方 TUI 立即显示并处理
  • 即时、无状态（不写库）、无 ack
  • 等效于「有人在终端里打字」
持久管道 · orchestration send
  • SQLite 信箱：INSERT INTO messages
  • 对方 check 主动拉取最老未确认批次
  • 落库可追踪：reply / ack / thread
  • 不 ack 就反复投递（at-least-once）
两条管道都在同一个 Orca Runtime 进程内（Electron 主进程或 orca serve），但数据通路零交集——一个走内核 PTY，一个走 SQLite 文件。选择发送方式 = 选择「即时送达」还是「落库追踪」。
实时管道：terminal send

终端的本质是 node-pty 创建的伪终端（PTY）。Runtime 为每个 Agent 终端 spawn 一个 PTY 实例：

JS · 主进程实际代码形态（截取）
pty.spawn({ cols: 120, rows: 40, cwd: e.worktree.path, // 工作区目录 command: O.launchCommand, // agent 启动命令 ...{ shellOverride: "wsl.exe" } // 某些环境走 WSL })

发送消息就是往 PTY master 端写字节流——按 handle 从注册表找到 PTY 实例，直接 write：

JS · terminalSend（截取）
terminalSend(handle, text) { const pty = registry.get(handle) // 按 handle 从注册表找 PTY 实例 pty.write(text + '\n') // 写 master = 等效用户击键 return { bytesWritten: text.length } }

PTY 生命周期由一组 IPC 通道管理，覆盖创建、数据、退出、重放、序列化与恢复：

IPC 通道（运行时协议）
pty.spawn / pty.attach / pty.data / pty.exit pty.replay / pty.serialize / pty.revive / pty.resize / pty.shutdown
特点：即时、无状态（不写库）、无 ack——发完就完，对方 TUI 立即显示并处理。消息丢了就是丢了，没有回执。
PTY 是什么：内核提供的模拟终端设备对

PTY 是一对内核设备：master 和 slave。Agent 的 TUI 打开 slave 端当 stdin/stdout；master 端由 Orca 持有——写 master = 往终端「按键」，读 master = 拿 Agent 的屏幕输出。

平台差异：Windows 走 ConPTY，Linux/macOS 走 /dev/ptmx。对终端侧来说，这种方式与真人打字无法区分——Agent 看到的就是正常的键盘输入流。

持久管道：orchestration send

发送的第一步是把消息写进 SQLite 的 messages 表：

SQL · 实际执行的核心语句（截取自打包代码）
INSERT INTO messages ( id, run_id, delivery_contract, from_handle, to_handle, subject, body, type, priority, thread_id, payload, read, sequence )

应用层封装很薄——组装消息对象，按收件地址选定投递合约，然后 INSERT：

JS · sendMessage（截取）
sendMessage({to, subject, body, type}) { const msg = { id: `msg_${randomId()}`, run_id: currentRun.id, delivery_contract: pickContract(to), // 关键：按地址选合约 from_handle: currentTerminal.handle, // 自动解析为调用者终端 to_handle: to, // run:xxx / dispatch:xxx / term_xxx read: 0, sequence: nextSequence() // FIFO } db.prepare("INSERT INTO messages (...) VALUES (...)").run(msg) }

收件地址决定投递合约（delivery_contract）——这决定了消息的能力上限：

地址contract效果
run:run_xxxcurrent_delivery标准持久信箱，可 reply/ack/thread
dispatch:<id>current_delivery精确派发，可跨服务器 relay
term_xxx（handle）legacy_direct轻量；绑定终端生命周期，接收方只能只读查看（提示 reply and acknowledgment are unavailable）

拉取侧是「取最老的未确认批次」——按消费代数排序，一次取一批：

JS · check（截取）
check(runId) { const d = db.prepare( "SELECT * FROM deliveries WHERE run_id=? AND status='outstanding' ORDER BY consumer_generation LIMIT 1" ).get(runId) if (!d) return { messages: [], count: 0 } return { deliveryId: d.id, messages: JSON.parse(d.message_ids).map(id => getMessage(id)) } }

处理完之后必须 ack——把批次状态翻转为 acknowledged：

SQL · ack
UPDATE deliveries SET status='acknowledged', acknowledged_at=now() WHERE id=?

把发送、投递、拉取、确认串起来，就是一条消息的完整生命周期：

消息生命周期
send（INSERT messages, sequence++） → 投递批次（deliveries: message_ids=JSON数组, status='outstanding'） → 接收方 check 拉取最老批次 → 处理完 check --ack（status → 'acknowledged'） → 不 ack 就每次都返回同一批（at-least-once）
未 ack 前同一批次反复返回 → 至少一次投递（at-least-once）；ack 后消息本身 read 置 1。代价是接收方必须容忍重复消息——这是 at-least-once 语义的标准交换。
配套实现：thread_id 线程、幂等账本与 priority

thread_id：reply --id X 生成的新消息带 thread_id=X，把问答串成线程——question_threads 的答案回链就是靠它。

mutation_receipts / mutation_receipt_ledger：操作幂等账本。--retry-request 重放时复用同一身份，同一操作不会被执行两次——网络重试场景下的 Exactly-once 副作用保障（投递仍是 at-least-once，但变更本身幂等）。

priority（normal/high/urgent）：影响唤醒顺序；read 是消息级已读标记，与批次级的 ack 相互独立。

表设计要点
runs一个 Run 只绑定一个 coordinator_handle（单协调者）；consumer_generation 是信箱已消费到第几代的标记
tasks.status 六态pending（建了没派）→ ready（依赖满足）→ dispatched（已派）→ completed/failed（结算）→ blocked（被 gate 卡住）

编排与 git 的协作边界

分工一句话：编排层记账，Agent 干活，git 只管历史。编排消息不进版本库，代码变更全在 worktree 的私有分支里发生，最后由标准 git 操作汇合：

两层分工 · 编排层 → git 层
编排层（Orca） git 层（Worker） ───────────── ───────────── run-create / task-create 无 git 动作 worker-start → worktree 里开终端 ────────▶ git worktree add（或复用） dispatch → 注入任务书 ───────────────────▶ Agent 在私有 worktree 里： cd <worktree> && git add/commit worker_done（摘要 + files-modified 元数据） ↑ 提交发生在 Agent 那边 worker-release → 收终端 git merge <分支> / push+PR ───────────────▶ master 指针汇合

三条边界把职责切干净：

编排层管什么
  • 消息、工单、派发、结算——全部记在 SQLite
  • worker_done 的 files-modified 只是元数据，不是代码
  • worktree 的 Orca 元数据（comment/状态）与 git 分支正交
编排层不碰什么
  • 编排消息不写进 git
  • 合并是标准 git 操作，编排不参与
  • 两边只通过「worktree 绑定 repo + 私有 HEAD」挂钩

总结与速查
git 边界 · 速查
① 两条独立管道，对应两种发送语义
terminal send 走 PTY 直写——即时、无状态、无 ack，与真人打字无法区分；orchestration send 走 SQLite 信箱——INSERT → check 拉取 → ack，落库可追踪。选择哪种，本质是选择「即时送达」还是「落库追踪」。
② 三个概念按生命周期分层
Run 是会话级容器（命名空间 + 协调者收件箱，不调度任何东西）；Task 是声明（描述「做什么」，无执行者）；Dispatch 是一次执行（派谁干、干得怎样）。run_id 是几乎所有表的关联键。
③ 投递是 at-least-once，确认靠显式 ack
不 ack 就每次 check 都返回同一批——接收方必须容忍重复消息。配套的幂等账本（mutation_receipts）保证重放不产生重复副作用。
④ 单协调者模型贯穿始终
run-create 自动绑定协调者终端，check 默认查绑定 Run；多编排者各自绑定互不干扰；share 一个 Run 时旧协调者被 fence（只读），需 takeover 才能接管消费权。
⑤ 编排记账，Agent 干活，git 只管历史
编排消息不进版本库；代码变更全部发生在 worker 的私有 worktree 分支里；合并是标准 git 操作，编排层不参与。两层只通过「worktree 绑定 repo + 私有 HEAD」挂钩。
