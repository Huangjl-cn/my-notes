问题：传统 RAG 不累积

2026 年，Andrej Karpathy 在一篇 gist 文章中指出了当前 LLM 知识系统的一个根本缺陷——大多数方案（ChatGPT 文件上传、NotebookLM、传统 RAG）共享同一个问题：

The LLM is rediscovering knowledge from scratch on every question. There is no accumulation.

每次提问，LLM 从原始文档中重新检索片段、重新推导。问一个需要综合五篇文档的问题，LLM 每次都要从头拼凑。知识不累积，不生长。每次对话结束后，产生的洞察消失在聊天历史中，下一次提问又从零开始。

核心矛盾：LLM 有能力综合、分析和关联知识，但传统交互模式将这些产出视为一次性消耗品——没有任何机制将"好的答案"沉淀为持久的知识资产。

方案：LLM 维护一个持久化 Wiki

Karpathy 的替代方案是让 LLM 增量构建并持续维护一个结构化的、相互链接的 Markdown 文件集合——一个 Wiki。这个 Wiki 位于用户和原始来源之间：

Rather than only retrieving from raw documents at query time, the LLM incrementally builds and maintains a persistent wiki — structured, interlinked markdown files sitting between the user and raw sources.

当新来源到达时，LLM 读取它、提取关键信息、整合到已有 Wiki：更新实体页、修订主题摘要、标注矛盾、强化或修正现有结论。知识编译一次，持续保持最新，而不是每次查询时重新推导。

关键洞察：Wiki 是一个持续复利的产物。交叉引用已经存在，矛盾已经被标注，综合结论已经反映了所有已读内容。每增加一个来源、每问一个问题，Wiki 更丰富一层。人类永远（或几乎）从不自己写 Wiki——LLM 处理全部簿记工作。

Karpathy 用一个精妙的类比概括了整个理念：

Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.

三层架构

Karpathy 将系统分为三个清晰的层次，每一层有明确的职责和操作者：

层内容谁操作说明
Layer 1: 原始来源文章、论文、图片、数据文件人类放入，LLM 只读不可变，事实的源头
Layer 2: WikiLLM 生成的 Markdown：摘要、实体、概念、对比、综合LLM 写，人类读知识积累的核心
Layer 3: SchemaCLAUDE.md / AGENTS.md——结构、约定、工作流人 + LLM 共同演化让 LLM 成为「有纪律的 Wiki 维护者」

这种分层设计的精妙之处在于：每一层的关注点完全隔离。人类不需要操心 Wiki 的维护（Layer 2），LLM 不需要操心来源的真伪（Layer 1），而 Schema（Layer 3）确保 LLM 的行为是可预测、可约束的——它不是一个通用聊天机器人，而是一个有纪律的 Wiki 维护者。

三种核心操作

围绕三层架构，Karpathy 定义了三种核心操作来驱动知识库的运转：

Ingest
摄取——人把来源放入原始集合，通知 LLM。LLM 读取 → 讨论关键发现 → 写摘要页 → 更新索引 → 更新相关实体/概念页 → 追加日志。单个来源可能触碰 10–15 个 Wiki 页面。
Query
查询——人提问，LLM 搜索相关页面 → 阅读 → 综合回答（带引用）。好的答案被归档回 Wiki，不消失于聊天历史。对比、分析和发现的关联都是有价值的产物。
Lint
整理——定期健康检查：页面矛盾、过期结论、孤儿页面、缺失的概念页、缺失的交叉引用、可通过网络搜索填补的数据缺口。随 Wiki 增长保持健康。

索引与日志：Wiki 的导航系统

两个特殊文件帮助 LLM 和用户导航不断增长的 Wiki：

index.md（内容导向）
Wiki 中所有内容的目录，按类别组织，每个条目带链接和一句话摘要。LLM 每次摄取后更新。查询时 LLM 先读索引找到相关页面，再深入阅读。在中等规模（~100 来源、~数百页）下运行良好，避免了对 embedding-based RAG 基础设施的依赖。
log.md（时间导向）
只追加的操作记录，记录发生了什么、何时发生。用一致的格式前缀（如 ## [2026-07-20] ingest | Article Title），可用 grep 等 Unix 工具解析。当 Wiki 增长到 index.md 不够用时，需要更强大的搜索工具。
为什么有效：Karpathy 指出，维护知识库最繁琐的部分不是阅读或思考，而是簿记。人类放弃 Wiki 的原因不是不会读或不会想，而是维护负担增长快于价值增长。LLM 不觉得无聊、不会忘记更新交叉引用、可以一次触碰 15 个文件——维护成本趋近于零。

Karpathy 将这一理念追溯至 Vannevar Bush 的 Memex（1945）——一个私人的、策展的知识存储，文档之间的关联与文档本身同等价值。Bush 没能解决的是"谁来维护"——而 LLM 恰好填补了这个空缺。

Layer 3：Schema 的重大扩展

Karpathy 的 Schema 层是一个 CLAUDE.md 文件，定义结构和约定。本仓库在此基础上做了大幅扩展——不只是"一个配置文件"，而是一整套技能体系：

contextual-prefix.py — Chunk 切分 + 上下文前缀

离线工具链的第一步：将每篇 Markdown 切分为可检索的 chunk，并为每个 chunk 生成上下文前缀——即告诉检索模型"这段话来自哪篇文章、关于什么"。

切分逻辑：正文按 \n\n（空行）切为段落，逐个累加，当累计字符数达到 CHUNK_TARGET_CHARS = 2000（约 500 token）时输出一个 chunk。下一个 chunk 开头回退 200 字符（CHUNK_OVERLAP_CHARS = 200），防止语义被割裂。页面过短（< 2000 字）则单 chunk 输出。

前缀生成采用三级架构，自动降级：

Tier条件前缀来源数据出境？
1ANTHROPIC_API_KEY 已设Anthropic Haiku API（prompt-cached）是（~$12/千页）
2claude 在 PATHclaude -p 子进程是（用 CC 订阅额度）
3（默认）以上都不满足页面 title + 第一句话合成否，纯本地

Tier 3 是仓库实际使用的模式——零成本、纯本地、不需要任何 API key。合成的前缀虽然不如 LLM 生成的丰富，但已经足够告诉检索模型 chunk 的来源和主题。

Tier 3 合成前缀格式与 chunk JSON 结构

Tier 3 合成前缀格式："This passage is from the wiki page "{标题}". The page opens: {正文第一句话}"

输出文件（.vault-meta/chunks/<address>/chunk-NNN.json）：

增量策略：body_hash / page_body_hash 用于检测内容变化。--all 只重新处理已变更的页面（hash 匹配则跳过），--rebuild 强制全量覆盖。

核心切分逻辑：

PYTHON · chunk_body — 段落边界感知的滑动窗口
def chunk_body(body, target_chars=2000, overlap=200): paragraphs = [p.strip() for p in re.split(r"\n\s*\n", body) if p.strip()] chunks = [] cur = [] cur_len = 0 for p in paragraphs: cur.append(p) cur_len += len(p) + 2 if cur_len >= target_chars: chunk_text = "\n\n".join(cur) chunks.append(chunk_text) # 下一个 chunk 开头回退 overlap 字符，防止语义割裂 tail = chunk_text[-overlap:] if overlap > 0 else "" cur = [tail] if tail else [] cur_len = len(tail) if cur and "".join(cur).strip(): chunks.append("\n\n".join(cur)) return chunks

按空行切分段落 → 逐段累加至 2000 字符 → 输出一个 chunk → 回退 200 字符作为下一个 chunk 的种子。页面过短则单 chunk 输出。Tier 3 前缀生成同样简洁：取页面 title 和正文第一句话拼接，纯本地、零成本。

PYTHON · synthetic_prefix — Tier 3 零成本前缀
def synthetic_prefix(fm, body, chunk_text): title = (fm.get("title") or "").strip() or "(untitled)" first_sentence = re.split(r"(?<=[.!?])\s+", body.strip(), maxsplit=1) first = first_sentence[0][:300] if first_sentence else "" return f"This passage is from the wiki page \"{title}\". bm25-index.py — BM25 倒排索引 + jieba 中文分词

角色：离线，将 chunk JSON 构建为可搜索的倒排索引。这是检索管线的第一级——BM25 召回 20 个候选，然后交给 rerank 精选 top-5。

BM25 是经典的稀疏检索算法（Okapi BM25，k1=1.5, b=0.75）。它的核心直觉：词越稀有（高 IDF）权重越高；词频有饱和效应（出现 5 次 vs 50 次差异不大）；长文档有惩罚项（避免长文档霸占结果）。

BM25 公式与分词逻辑

BM25 公式：

Score(q, d) = Σ IDF(term) × [ TF × (k1+1) ] / [ TF + k1 × (1-b + b×dl/avgdl) ]

其中 IDF = ln(1 + (N - df + 0.5) / (df + 0.5))——N 为总文档数，df 为该词出现的文档数。

分词逻辑（tokenize）——按 Unicode 归属分别处理：CJK（U+4E00-U+9FFF 等）字符走 jieba.cut() 分词，过滤单字和纯标点；非 CJK 走正则 \w[\w'\-]* 提取词干，过滤 stopwords（a, the, is, …）和单字母。

这种中英文双轨分词是仓库对中文内容的关键优化——v1.7 原版用 bigram 产生大量垃圾 token，切换 jieba 后词表从 9,466 降到 3,836（0% 垃圾）。

PYTHON · _append_cjk_tokens — jieba 分词
def _append_cjk_tokens(tokens, seg): import jieba for word in jieba.cut(seg): word = word.strip() # 过滤单字（太宽泛）和纯标点 if len(word) < 2: continue if all(ch in "，。！？；：""''（）【】《》…—～、・　 " or ch.isspace() for ch in word): continue tokens.append(word.lower())
索引数据结构与查询流程

索引文件（.vault-meta/bm25/index.json）结构：

JSON · BM25 索引结构
{ "doc_count": 115, "avg_dl": 246.2, "params": {"k1": 1.5, "b": 0.75}, "vocab": { "animation": { "df": 12, "postings": [["c-000033:0", 5], ["c-000022:0", 3]] } }, "docs": { "c-000033:0": {"path": ".vault-meta/chunks/c-000033/chunk-000.json", "dl": 87} } }

df=12 表示 "animation" 出现在 12 个 chunk 中；["c-000033:0", 5] 表示在 chunk c-000033:0 中出现了 5 次。查询时 bm25-index.py query "text" --top 20 走同样的 tokenize + IDF/TF 算分流程。BM25 索引始终全量重建（纯 Python，115 docs < 1s），通过 fcntl.LOCK_EX 保证并发写入安全。

PYTHON · BM25 query — IDF/TF 计分
def query(text, top_k=20): idx = load_index() N = idx["doc_count"] avg_dl = idx["avg_dl"] or 1.0 k1, b = 1.5, 0.75 qterms = tokenize(text) scores = defaultdict(float) for term in qterms: v = vocab.get(term) if not v: continue df = v["df"] idf = math.log(1 + (N - df + 0.5) / (df + 0.5)) for cid, cnt in v["postings"]: dl = docs[cid]["dl"] denom = cnt + k1 * (1 - b + b * dl / avg_dl) scores[cid] += idf * (cnt * (k1 + 1)) / denom ranked = sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:top_k] return [{"chunk_id": cid, "score": round(s, 6), ...} for cid, s in ranked]

rerank.py — 语义重排

角色：在线，被 retrieve.py 作为 Python 模块导入（非子进程）。对 BM25 召回的 20 个候选进行语义重排，返回 top-5。

模型配置：使用 qwen3-embedding:0.6b（600M 参数，中文优化，1024 维向量），通过 Ollama 本地部署。支持双 API 回退：优先 v2 API（/api/embed，qwen3 等新模型需要），回退 v1 API（/api/embeddings，nomic-embed-text 等老模型）。

重排流程清晰简洁：Ollama 探活（3 秒超时）→ embed query → 对每个候选 chunk 查 embed-cache（key = {model}:{body_hash}）→ 未命中则调用 embedding 并写缓存（原子写入：tmp + os.replace）→ 计算 cosine 相似度 → 降序返回 top-N。

embed-cache 的价值：chunk 内容不变 → body_hash 不变 → 不重复调用 Ollama。换 embedding 模型时缓存自动失效（key 前缀变了）。首次 ~200ms/chunk，缓存命中 ~0ms。安全守卫：OLLAMA_URL 若非 localhost 地址则拒绝连接——防止数据意外出境。
embed_one 双 API 回退与 cosine 相似度

Ollama 的 v1 和 v2 API 返回格式不同——qwen3 等新模型需要 v2 的 /api/embed（返回 {"embeddings": [[...]]}），nomic-embed-text 等老模型走 v1 的 /api/embeddings（返回 {"embedding": [...]}）。实现上优先 v2、异常时回退 v1：

PYTHON · embed_one — 双 API 自动回退
def embed_one(url, model, text): # v2 API: /api/embed（qwen3 等新模型） try: payload = json.dumps({"model": model, "input": text}).encode("utf-8") req = urllib.request.Request(f"{url}/api/embed", data=payload, ...) with urllib.request.urlopen(req, timeout=30) as resp: data = json.loads(resp.read()) embeds = data.get("embeddings") or [[]] return embeds[0] if embeds else [] except urllib.error.HTTPError: pass # 回退到 legacy API # Legacy API: /api/embeddings（nomic-embed-text 等老模型） payload = json.dumps({"model": model, "prompt": text}).encode("utf-8") req = urllib.request.Request(f"{url}/api/embeddings", data=payload, ...) with urllib.request.urlopen(req, timeout=30) as resp: return json.loads(resp.read()).get("embedding") or []

Cosine 计算干净利落——不到 10 行，无外部依赖：

PYTHON · cosine — 向量相似度
def cosine(a, b): if not a or not b or len(a) != len(b): return 0.0 dot = sum(x * y for x, y in zip(a, b)) na = math.sqrt(sum(x * x for x in a)) nb = math.sqrt(sum(y * y for y in b)) if na == 0 or nb == 0: return 0.0 return dot / (na * nb)

retrieve.py — 查询编排器

角色：在线，wiki-query 调用的唯一入口。零子进程架构——用 importlib 把 bm25-index.py 和 rerank.py 作为 Python 模块动态导入，一次查询只有一次 Python 进程启动。

Windows Git Bash 编码修复（_fix_argv_encoding）：Git Bash 可能将 UTF-8 参数按 ANSI 解码导致中文乱码。该函数通过 latin-1 字节回退再 UTF-8 重解码修复。这是仓库在 Windows 环境下反复踩坑后沉淀的工程经验。

零子进程架构的核心——import_sibling：用 importlib 将带连字符的 .py 文件名动态加载为 Python 模块对象，避免子进程开销：

PYTHON · import_sibling — 零子进程模块导入
def import_sibling(name, filename): target = SCRIPTS_DIR / filename if not target.is_file(): log(f"ERR: sibling helper {filename} not found") sys.exit(EXIT_NOT_PROVISIONED) spec = importlib.util.spec_from_file_location(name, target) mod = importlib.util.module_from_spec(spec) spec.loader.exec_module(mod) return mod

一次查询只启动一次 Python 进程——BM25 查询毫秒级，rerank 耗时主要取决于 Ollama embedding 速度。相比子进程方案，避免了每次调用的进程创建/销毁和序列化开销。

辅助脚本：tiling-check.py + Shell 工具

tiling-check.py（语义平铺检测）：离线运行，使用与 rerank.py 相同的 embedding 接口检测 Wiki 中语义重复的页面对。cosine ≥ 0.90 → 严重重复；0.80–0.90 → 建议人工检查。阈值配置在 .vault-meta/tiling-thresholds.json，按模型区分。

tiling-check.py — 嵌入循环与缓存逻辑

核心循环对每个 wiki 页面计算 embedding 并检测语义重复。通过 body_hash 判断内容是否变化，命中缓存则跳过昂贵的 embedding 调用：

PYTHON · run_check — 缓存感知的嵌入循环
for md in sorted(WIKI_DIR.rglob("*.md")): text = md.read_text(encoding="utf-8") fm, body = parse_frontmatter(text) rel = md.relative_to(VAULT_ROOT).as_posix() h = body_hash(body, model) # sha256(model + body) entry = cache["embeddings"].get(rel) if entry and entry.get("hash") == h: pages.append((rel, entry["embedding"])) # 缓存命中 cached_hits += 1 continue emb = embed(body, model, ollama_url) # 调用 ollama cache["embeddings"][rel] = {"hash": h, "embedding": emb} pages.append((rel, emb)) computed += 1

随后对 page 做 O(n²) 的 cosine 交叉比对——cosine ≥ 0.90 标记为严重重复，0.80–0.90 建议人工检查。缓存使后续运行大幅加速：首次 ~N 次 ollama 调用，之后仅重新嵌入有变化的页面。

核心三操作详解

Karpathy 的 Ingest / Query / Lint 在仓库中对应三个最核心的 Skill，每个都有完整的 subagent 架构和细致的工程考量：

/wiki-ingest — 摄取：每个来源独立派一个 subagent（claude-obsidian:wiki-ingest），可并行处理多个文件。单次摄取的完整触达范围印证了 Karpathy 说的 "a single source might touch 10–15 wiki pages"：

→
wiki/sources/<slug>.md ← 来源摘要页（新建）
→
wiki/concepts/<Concept>.md ← 提取的概念（新建或更新）
→
wiki/entities/<Entity>.md ← 提取的实体（新建或更新）
→
wiki/index.md ← 追加索引条目
→
wiki/log.md ← 顶部追加操作日志
→
wiki/hot.md ← 更新近期上下文缓存
→
子索引（_index.md）+ .raw/.manifest.json ← 记录摄取状态

所有写操作前通过 wiki-lock.sh acquire 获取排他锁，避免并行 ingest 冲突。

/wiki-query — 查询：设计了三档深度以适应不同场景：

模式触发读取范围Token 预算
Quick简单事实查询hot.md + index.md~1,500
Standard（默认）大多数问题hot.md + retrieve.py top-5~3,000
Deep"comprehensive" / "tell me everything"hot.md + retrieve.py + 全面阅读~8,000+

标准流程：Read(hot.md) → retrieve.py query（BM25 + rerank）→ Read(candidate pages) → 综合回答（带 [[wikilink]] 引用）→ 建议归档。当 retrieve.py 不可用时自动回退 v1.6 手动翻页模式。

/wiki-lint — 健康检查：派 subagent 做全库扫描，检查维度包括：孤儿页面（0 入链）、死链接、过期声明、缺失交叉引用、Frontmatter 缺失、空 section、语义重复（通过 tiling-check.py）。

扩展操作（一）：autoresearch + save

/autoresearch — 自主研究循环：灵感来自 Karpathy 的 autoresearch 模式。通过可配置的 program.md 定义研究目标，循环运行直到达到深度。

三轮架构：

1
Broad search（广撒网）——topic 分解为 3–5 个搜索角度，每个 2–3 次 WebSearch，取 top 2–3 结果 WebFetch，提取观点、实体、概念、矛盾
2
Gap fill（补缺口）——识别 Round 1 的缺失和矛盾，至多 5 次针对性搜索 → WebFetch → 补充
3
Synthesis check（可选）——如果仍有重大矛盾或缺口 → 再一轮；否则 → 开始归档

归档产物覆盖 sources、concepts、entities、questions 四类页面，然后更新 index、log、hot。预算约 3 轮 × 5 来源 × 3 角度 ≈ 45 次 WebFetch。v1.8.2+ 增加了内容安全措施——剥离 <script>、<iframe>、<style>，转义 [[ 和 ]]（防 wikilink 注入），拒绝正文中的 frontmatter 分隔符。

/save — 保存对话洞察：Karpathy 原话 "good answers filed back into the wiki" 的精确实现。触发词 "save this" / "保存这个" → 分析当前对话 → 判定内容类型（概念/问答/会话/见解）→ 生成 YAML frontmatter → 按 wiki-mode 路由到目标目录 → 更新 index + log + hot。

扩展操作（二）：canvas + think + wiki-fold + wiki-mode

/canvas — 可视化画板：底层使用 Obsidian 的 .canvas JSON 文件（遵循 jsoncanvas.org 开放标准）。结构简洁——节点 {id, type, x, y, width, height, color} + 边 {fromNode, toNode} + 分组 {type: "group", label}。默认画布 wiki/canvases/main.canvas，zone 自动分区。

/think — 十原则思考循环：把 Karpathy 说的人类角色——"think about what it all means"——框架化。8 个检查点：OBSERVE → LISTEN → THINK → CONNECT → FEEL → ACCEPT → CREATE → GROW，确保不跳步、不自欺、不回避不确定性。

/wiki-fold — 日志折叠：log.md 积累太多条目时，把最近的 2ᵏ 条压缩成摘要页。双模式：dry-run（stdout 预览）和 commit（Write/Edit 写盘）。fold 是纯增量操作，不修改或删除原始 log。

/wiki-mode — 方法论路由：支持四种知识组织方法论——Generic（默认）、PARA、LYT、Zettelkasten。wiki-ingest、save、autoresearch 在创建页面前会调 wiki-mode.py route <type> "<topic>" 获取目标路径，确保不同方法论下的文件落在正确位置。

wiki-mode 路由示例：不同方法论对同一内容类型的路径映射
内容类型GenericPARALYTZettelkasten
新来源wiki/sources/foo.mdwiki/resources/<topic>/foo.mdwiki/notes/foo.md + 更新 MOCwiki/<ID>-foo.md
新概念wiki/concepts/Name.mdwiki/resources/concepts/Name.mdwiki/notes/Name.md + concept MOCwiki/<ID>-name.md

关键技术决策

仓库在工程实现过程中做了几个值得展开讨论的技术决策：

中文优先的检索栈：从 v1.7 的 bigram + nomic-embed-text 切换到 jieba + qwen3-embedding 是一次彻底的升级。实测效果：qwen3 将相关页面得分提升 7–8%，不相关页面压低 9–16%，区分度显著优于 nomic-embed-text（137M，英文优先）。

v1.7 原版
  • Bigram 分词：词表 9,466 / 80% 垃圾
  • nomic-embed-text (137M, 英文优先)
  • 768 维向量
  • /api/embeddings（旧 API）
当前版本
  • Jieba + Qwen3：词表 3,836 / 0% 垃圾
  • qwen3-embedding (600M, 中文优化)
  • 1024 维向量
  • /api/embed（新 API），双 API 回退

零子进程查询：retrieve.py 用 importlib 动态导入 BM25 和 rerank 模块，一次查询只有一次 Python 进程启动。BM25 查询毫秒级，rerank 耗时主要在 Ollama embedding（首次 ~200ms/chunk，缓存命中 ~0ms）。

三层回退保障：ollama 可达 + 模型已 pull → BM25 + cosine rerank（最优）→ ollama 不可达 → BM25 only（可用）→ BM25 索引不存在 → exit 10 → wiki-query 退 v1.6 翻页（兜底）。任一层失效都不影响基本功能。

缓存位置失效条件

增量更新策略——chunks：只处理 page_body_hash 变化的页面（--all 增量，--rebuild 全量）；BM25 索引：始终全量重建（廉价，< 1s）。
